    Dump and routing¶

    dump.py turns an official dump into the chunk files the pipeline processes; scholarly.py decides which entities go into the scholarly set. Download, split and route run on the main set's directory only, and refuse WIKIDATA_SCHOLAR.

    Download¶

    latest_release() reads the directory listing of dumps.wikimedia.org and returns the newest date whose directory holds wikidata-{date}-all.json.bz2 (or .gz, by DUMP_FORMAT; the newest directories can lack it while the dump is still being written).

    download() fetches the release's md5 sums, then the dump into DUMP_DIR with HTTP range requests: the bz2, or with WIKIDATA_DUMP_FORMAT=gz the gz (DUMP_FORMAT), whose md5 is in the same file. It fetches the dump in pieces of PIECE (32 MiB), each one range request, over WIKIDATA_DUMP_CONNECTIONS kept-alive connections at once (MAX_CONNECTIONS, 3, by default, and never more), and appends the pieces to a .part file in order, holding at most WINDOW (2) pieces per connection in memory until their turn (192 MiB with 3). So the .part is always the dump's first bytes: split-dump follows it, and a rerun resumes from its size, whatever number of connections wrote it. A failed request is retried (on a new connection, backing off to a minute), and a 429 or 503 waits for its Retry-After. The finished file is checked against its md5 before being renamed into place. Requests carry a descriptive User-Agent (USER_AGENT): Wikimedia answers 403 to urllib's default.

    dumps.wikimedia.org says: "Downloads are also rate limited and capped at 3 connections per-IP. [...] Clients that do not respect the user-agent policy or who try to evade these limits may be blocked." Its limit is per connection, about 5 MB/s each, so 3 connections take about 15 MB/s: the bz2 in about 2 hours rather than 4 to 5½. The cap counts every connection from the IP, so don't run a second download from it alongside.

    WIKIDATA_DUMPS_URL takes the dump from a mirror (the md5 sums still come from dumps.wikimedia.org). Two mirrors on Wikimedia's list carry the current Wikidata entity dumps, with the same files and md5s:

    Mirror WIKIDATA_DUMPS_URL MB/s from a GitHub runner, 1 / 3 connections
    Your.org (Illinois) https://dumps.wikimedia.your.org/wikidatawiki/entities 55-93 / 125-138 (297 / 705 for a range just fetched)
    ACC, Umeå University (Sweden) https://ftp.acc.umu.se/mirror/wikimedia.org/other/wikibase/wikidatawiki 2-9 / 1.4-19
    dumps.wikimedia.org (the default) 5.2 / 14-15

    These are from a runner in a data centre (October 2026); a home link may be slower than any of them, and a mirror helps only on a link faster than dumps.wikimedia.org's 15 MB/s (120 Mbit/s). Your.org takes the bz2 in under 15 minutes from a runner, and the gz in about 20, so the split (2h47m from the bz2, 54m from the gz on 4 cores) is all a release waits for: from Your.org, the gz is the faster dump to take, at 53 GB more disk.

    Split¶

    split() streams the dump through its decoder (DECODERS): lbzip2 -dc (all cores) for the bz2, and for the gz the first installed of igzip, pigz and gzip, each on one core. Decoding is most of the split's CPU time from the bz2, 160-210 CPU s per GB on a 4-core CI runner; igzip takes 5-8 CPU s per GB of gz, pigz 15-21 and gzip 25-30. The gz dump is 1.5 times the bz2's size (156.6 GB against 103.5 GB for 20261020). The chunks and manifests are the same from either, so a split resumes from either. The split groups the entity lines into batches of CHUNK_ENTITIES (10,000, the size of the philippesaade files), and hands each batch to a process pool that writes chunk_{N}.parquet (zstd level 9, about the size of the bz2). At most MAX_PENDING_BYTES (4 GiB) of decompressed lines wait for the workers, which bounds memory. Each finished chunk appends its manifest line; a rerun skips the chunks already in the manifest, and split.done marks the end.

    Each entity becomes a row with the columns the process step reads (entity_row):

    Column Content
    id the entity id
    labels, descriptions JSON {lang: value} (the dump's {lang: {language, value}})
    aliases JSON {lang: [value, ...]}
    sitelinks JSON, as in the dump (site, title, badges)
    claims JSON, each snak's datavalue replaced by its value, with the value's type as datavalue_type
    entity JSON of the entity's own fields: type, datatype (properties), ns, title, pageid, lastrevid, modified

    Everything else in the dump is kept as it is: snak types and hashes, statement ids and types, qualifiers-order, references with their hash and snaks-order, sitelink badges, and item values' entity-type and numeric-id. The term reshaping relies on each term's language repeating its key; an entry where it does not is counted in the manifest's mismatched_terms. The dump writes an empty map as [], which _map reads as {}.

    The manifest also lists the field names found in each chunk's entities and sitelinks. split_manifest(), which every later step reads, halts if any of them is missing from EXPECTED_FIELDS. A field there that process.py does not read would otherwise be dropped without notice.

    Scholarly works¶

    An entity is scholarly if any of its "instance of" (P31) main-snak values is in SCHOLARLY_CLASSES: 43 classes. 37 of them are classes that philippesaade's copy of 2026-05-07 had left out almost entirely (at least 99% of their entities missing), such as scholarly article, doctoral thesis, erratum and preprint. The other 6 were partly missing and are scholarly works too: scientific publication, geological map, scholarly conference abstract, technical report, book review and scholarly chapter. scripts/p31_survey.py produced the figures, and the journal entry of 2026-10-01 records them.

    is_scholarly finds the P31 values with a regular expression on the claims JSON (P31_SNAK) rather than decoding it, which keeps routing fast. The expression is anchored on "mainsnak", so a qualifier's P31 does not count, and allows no { before the datavalue, so the match stays inside one main snak. This depends on the split writing datavalue after the snak's other keys.

    Route¶

    route() runs 8 workers (ROUTE_WORKERS), each reading one split chunk and writing its scholarly and other rows to routed/chunk_{N}.parquet in the scholarly and main data directories. An empty part is not written. A chunk's result is appended to route.jsonl (and fsynced) before the split chunk is deleted, so an interrupted route resumes from the log.

    Once every chunk is routed, each set's non-empty parts are renumbered from 0 in split order: groups are ranges of consecutive chunk numbers, so the numbers must have no gaps. The split's manifest is kept as manifest.split.jsonl, each set gets a manifest of its own parts (with split_chunk, the number it came from), the parts move to their new names, and both sets get split.done and route.done. split_manifest() refuses to run without route.done.

    The pull step for a release¶

    A release's chunks are already local, so its pull step is check_chunk(): the chunk file must exist with the manifest's size, and the chunk's state moves to PULL. chunk_sizes() gives the manifest's sizes to the group sizing.
