# 2026-09-30: Sorting the Hub tables by id

## Current State

### Row order on the Hub (measured on hub/, the local copy)

- Compaction writes each key's rows in source chunk order (docs/journal/2026-09-29-hub-layout-and-compaction.md), and no table is sorted by id.
- The source chunks run through the id space several times: of the 31 claims files, those starting at chunks 0000, 0884, 1593, 1864, 2572, 2809, 3553, 4552, 5562 and 6283 each have a minimum Q id below 82,000, and each file's Q ids cover a range of 8 to 139 million ids. Every claims file's Q id range overlaps the previous file's.
- Within each claims file the Q ids mostly ascend: 3-4% of consecutive Q rows step down (e.g. 1,237,666 of 37,044,710 in chunks-1284-1592). P rows (849 to 15,405 per file) are interleaved with the Q rows.
- claims row groups have narrow string id ranges within one ascending run (rg 10 of chunks-0000-0088: `Q521320` to `Q586048`) and span P and Q ids once P rows enter a row group (rg 50: `P178` to `Q5927142`).
- labels/en (2 files, 19 row groups in the first) has string id min/max of about `P100x` to `Q99999xx` in every row group, and 24% of its consecutive Q rows step down; links/enwiki (1 file) has 23%.
- A lookup of one id by string min/max statistics skips no labels/en row group, and opens every claims file whose footer range contains it.
- Each claims entity's rows are contiguous (3,405 id runs for 3,405 ids in row group 0 of the first file).

### Columns

- labels, descriptions, aliases: `id`, `language`, `value`; links: `id`, `site`, `title`; claims: `id`, `property`, `datavalue`, `datatype`, `rank`, `references`, `qualifiers`; claims_labels: `field`, `ref`, `language`, `label`.
- The row order within an id carries meaning in aliases (alias order) and claims (statement order), and a stable sort keeps it.

### Parquet statistics and id order

- Row group and page statistics on `id` are string min/max, so pruning follows string order (`Q10` < `Q9`).
- In numeric order, ids of the same digit count are also in string order, and a row group spanning a digit-count boundary (e.g. `Q999990` to `Q1000010`) has string min `Q1000000`-ish and max `Q999999`-ish, covering nearly every id — one such row group per boundary, up to 9 per key for Q ids.
- Keys of one row group (most keys other than en, mul and a few large languages) gain nothing from row group statistics; the page index (written by compaction) lets a reader that uses it prune pages within the row group, and Polars 1.44.2 does not (below).

### Sort cost

- 3,374 of the 3,376 keys are one file; labels/en is 2 files (699,860,818 bytes) and claims/all 31 (18,093,322,230 bytes, 774,255,243 rows).
- A claims row group of about 295k rows is 128 MiB of Arrow memory (`COMPACT_ROW_GROUP_BYTES`), so claims/all is on the order of 300 GB in Arrow memory, and sorting it across files needs a pass that splits rows by id range before sorting each range.
- The compaction check `_fingerprint` hashes rows with their index, so it fails on reordered rows by design.
- Polars 1.44.2 `scan_parquet(f).sort("id", maintain_order=True).sink_parquet(...)` on one claims file (`chunks-7263-7448`, 276 MB, about 6 GB in Arrow memory) was killed at a 4 GB memory limit, with and without `POLARS_FORCE_OOC=1`, and wrote nothing to `POLARS_TEMP_DIR`: its streaming sort holds its whole input in memory.

### Writer and reader support (pyarrow 25.0.1, polars 1.44.2)

- `pq.ParquetWriter`/`write_table` take `sorting_columns`, `bloom_filter_options`, `column_encoding`, `use_dictionary` (bool or column list), `max_rows_per_page` and `write_page_index`; a file written with `sorting_columns=[SortingColumn(0)]` has it in each row group's metadata.
- Polars 1.44.2 does not set a column's `SORTED_ASC` flag from `sorting_columns`, on `read_parquet` or `scan_parquet`.
- `sorting_columns` declares the order of the column's stored values, so for a string `id` it is true only of string order.

## Design

- A sort stage after compaction, which is left as it is, reading each table from the local copy (hub/) and committing replacement files through the compaction commit and verify path, with its own ledger.
- Sort key: `id` in string (byte) order, stable, so rows of one id keep their order; claims_labels by `ref`. Each row group declares `sorting_columns` on the sort column.
- A key's rows are sorted across all its files, so files cover consecutive id ranges.
- A key whose rows fit in memory (every key but claims/all) is read whole, sorted, and split into files of about `COMPACT_FILE_BYTES`; a one-file key stays one file.
- claims/all: the id column alone gives bucket boundaries of equal row counts; one streaming pass writes each row to its bucket; each bucket is sorted in memory and written with the final writer settings; consecutive buckets are then packed into output files of at most about `COMPACT_FILE_BYTES` by their written size, so each file is within one bucket of the target.
- Files are named `part-{i}-of-{n}.parquet`, zero-padded to the width of `n` (the Hugging Face convention).
- No Bloom filters.
- Writer settings as compaction's `_write_file`: row groups of `COMPACT_ROW_GROUP_BYTES` (128 MiB of Arrow memory, within the Hub's 100-300 MB row group guidance), dictionary encoding, ZSTD 3, page index, content-defined chunking. Smaller row groups and DELTA_BYTE_ARRAY are not used: the row group size follows the Hub guidance, and DELTA_BYTE_ARRAY reads slower in Polars.
- Check: rows equal as a multiset (row hash sums without the row index), the output sorted by the sort column, and each id's rows in their source order.
- Keys over 2 GiB of Parquet (only claims/all; labels/en is 700 MB, descriptions/en 490 MB) take the bucket path; every other key is sorted in memory and written as `ceil(bytes / COMPACT_FILE_BYTES)` files of equal rows (2 for labels/en, 1 for the rest).
- Bucket path, each pass resumable: boundaries from the key's distinct ids and their row counts, one bucket per ~64 MiB of source Parquet (about 280 for claims); one pass over the source row groups writing each row group's rows to their bucket files in source order (stable), so a bucket holds each of its ids' rows in source order; each bucket sorted and written with the final settings, and listed with its size; consecutive sorted buckets grouped into `ceil(total / COMPACT_FILE_BYTES)` files by cumulative written size and rewritten into the output files, row groups re-cut across bucket boundaries.
- Checks, in-memory path: the key's output files against its source files, by row hash sums with each row's rank within its id (multiset and order within id), and sorted within and across files. Bucket path: each sorted bucket against its bucket file by the same ranked sums; each output file against its sorted buckets by the ordered compaction `_fingerprint`; all output files against the source files as a multiset; sorted within and across files.
- Stages in `state/sort.jsonl`: sourced (hub/{table} downloaded and every file equal to the Hub's by size and sha256, with no extra local files), written, committed (each key's part files added and its chunks files deleted in one commit, keys batched as in compaction), verified, done (metadata JSON rewritten, hub/{table} replaced by the sorted files so the local copy matches the Hub).
- The sourced stage refuses a table with no hub/{table} (the local copy comes from `download-wikidata`). Once a table's copy is checked, its emptied compaction source directory `compact/src/{table}` is removed, and `compact/src` once empty. Compaction's bookkeeping (`compact/out/{table}/manifest.jsonl`, `files.jsonl`) and the sort's are kept; `compact/` is gitignored as a working directory, as `state/` is.
- Working files in `compact/sort/{buckets,out}/{table}`; `finalise-wikidata` runs the sort stage on each table after compaction; `compact._write_file` gains an optional `sorting_columns` argument, passed through to `ParquetWriter` (default None, as before).

### Sort stage (src/wikidata/sort_by_id.py), local test without the Hub

- `sort_table` runs the stages above; `finalise` runs it on each table after all tables are compacted, and it refuses a table whose compaction stage is not done.
- `write_table` on a test copy (labels/cy, claims_labels/cy, links/cywiki, and claims/all made of the first row group of `chunks-0000-0088` and of `chunks-0884-1031`, 497,027 rows), with small limits to force the bucket path and several files:
  - labels/cy (limit 20 MB per file): `part-0-of-2` and `part-1-of-2`, 13.2 and 14.5 MB; claims_labels/cy one 16.1 MB file sorted by `ref`; links/cywiki one 5.2 MB file; each equal to the source sorted by Polars `sort(col, maintain_order=True)` (`DataFrame.equals`), with `sorting_columns` in its row groups.
  - claims/all through 18 buckets (27,538 to 27,688 rows each) packed into 4 files of 3.44, 2.70, 3.75 and 2.77 MB (limit 4 MB), equal to the source taken by a numpy stable argsort of its ids (`Table.equals`).
  - After removing the manifest, the last two `files.jsonl` entries and the fourth file, a rerun left the buckets, sorted buckets and first two part files unchanged (same mtimes) and rewrote the rest.
- `_ranked` changes when two rows of one id swap and not when ids move; `_multiset` does not change when two rows swap.
- A bucket file is deleted once its sorted bucket is checked.
- String order kept over numeric order and over an added integer id column (2026-09-30): exact min/max pruning and a true `sorting_columns`; numeric order would leave row groups and files that cross a digit-count boundary unprunable and make `sorting_columns` false. File names carry no id range: in string order a range such as `Q1` to `Q1076543` includes `Q10765430` and excludes `Q2`.
